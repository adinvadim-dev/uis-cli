# Autodial coverage

Inventory and production evidence: 2026-10-30. Outgoing campaigns are distinct from advertising `campaigns`. The official [outgoing API index](https://comagic.github.io/data_api/auto_calls/) has four methods, merged by `make spec` and generated by `make gen`. Call API origination parameters named campaign_* do not establish campaign CRUD. Call origination and audio preview incur calls and were never invoked.

Private contracts were recovered from the supervisor frontend (build 2026-10-19), including AutoCallStore/CampaignModel/ExcludedNumbersStore, editor readiness checks, shared @comagic/core HTTP handling, ScenarioStore, ScheduleStore and PhoneListStore. Supervisor base: `https://uis-prod-msk-comagic-supervisor-workplace-api.uiscom.ru/v1/common`; cabinet RPC: `https://dataapi.uiscom.ru/v2.0`; caller lists use the existing Go billing cookie on `https://uis-prod-msk-comagic-api.uiscom.ru`. Source observation is not a provider stability guarantee. Production reads and bounded writes below used the existing bound private session; no Data API key was available or required.

`verified-live` means the named provider operation actually succeeded and its result was read back. The evidence column distinguishes real CLI runs from direct contract probes. `dry-run-only` describes live verification limits for operations that could dial; those status commands are implemented and available with confirmation. No actual customer calls, audio previews or spend were initiated.

## Campaign input and write semantics

Create requires a nonblank unique test marker/name, nonempty employee_ids and phone_list, future begin_date (`YYYY-MM-DD HH:MM:SS` in account timezone), number_capacity_usage_rule and its matching caller ID. Fixed uses number_capacity_id; random/random_from_group uses number_capacity_group_id; carousel uses pure_ani_phone_list_id. Resolve real references through the directories first. The CLI validates employee/caller membership and numbers before dispatch. It intentionally rejects past/immediate creation; explicit start handles activation.

The cabinet's Create button starts/schedules a campaign, not an empty draft. Passing status=draft does not create a draft. CLI input rejects status/new_status and read-only fields; status changes use the separate command. Defaults follow the editor: subscriber window 10:00–20:00, two retry intervals 00:15:00/00:30:00 per outcome, audio/prediction disabled. Optional fields: end_date, first_call_direction, subscriber_dialing_timeout, good_call_min_duration, after_call_employee_busy_max_duration, subscriber_to_employee_ratio, predicted_talk_duration, is_use_subscriber_timezone, is_outside_processing_enabled, is_predict_enabled, is_subscriber_message_enabled, subscriber_playlist.items, funnel_mark_ids, auto_mark_id, target_auto_mark_id. Attempts keys are subscriber_busy, subscriber_not_responsible, subscriber_number_problems, other. Subscriber windows/timezone and date range are the observed schedule; employee activity affects available execution capacity. Returned max_parallel_calls_count is not a proven writable field.

Update merges editable fields into current settings. Once planned/running/paused, only phone_list and employee_ids are accepted; terminal campaigns are not editable. Replacing phone_list logically removes omitted eligible rows via RPC before PUT, so it is a compound, non-atomic operation. Any uncertain partial result returns exit 9 with campaign_id. Successful/finalized contact rows cannot be cleared. Clear is logical removal, never historical erasure.

Supervisor POST/PUT succeed with an empty HTTP 200 response. Create takes a before/after exact-name inventory to recover one fresh identity, then compares the saved settings; update reads back its requested changes. A missing/ambiguous identity or unobserved field returns outcome_unknown (9), without replay. RPC mutation acknowledgement is result.data={} with metadata={} (legacy success=true also accepted); a separate get.auto_call_campaigns must prove the requested status/contact effects. Acknowledgement alone is insufficient. On exit 9 retain the private payload/marker/journal, reconcile the known campaign_id and stop automatic retries.

Status aliases use live next_statuses: draft → planned/in_process/cancelled; planned → in_process/cancelled; in_process → paused/completed/cancelled; paused → in_process/completed/cancelled. Completed/cancelled are terminal. stop means pause; complete is terminal completion; cancel is terminal cancellation. A repeat of the current status is a verified no-op. Direct generated RPC commands retain provider-level semantics; the high-level aliases additionally enforce transition metadata.

## Production lifecycle and remaining proof limits

The initial empty-draft probe returned HTTP 500 (root value_error.exception), no ID and no exact-marker match. Source investigation then established that its DTO was invalid: the editor requires recipients, employees and caller ID. After read-only reconciliation, a corrected full request with the same marker created exactly one campaign, planned for 2099. No in_process request was sent. Creation HTTP 200/empty, GET, PUT contact/employee edits, synthetic RPC additions/removals and cancellation all succeeded. A planned→paused PATCH returned 500 and changed nothing; that path is not used by high-level status commands. Planned date/attempt/window edits were also ignored, so the CLI rejects them. A DELETE of the owned cancelled resource returned 405.

The owner authorized one cancelled residue. Final read-back: cancelled, zero active contacts; synthetic rows retained as deleted history. The private durable lifecycle journal records all dispatches and observations outside Git; it contains ownership IDs/reference data and is not published. Existing business campaigns were used for reads only. No second test campaign is authorized by routine reruns.

The command-level suite requires live reads/CSV/XLSX parsing and keyless RPC listing. Exclusion writes and fresh campaign writes have independent opt-ins and exclusive fsynced journals. Fresh CLI creation is not implied by a direct provider probe. The owned-journal reconciliation probe checks the already cancelled fixture and repeat clear/cancel no-ops without creating another resource. Start/resume and audio remain untested live under the no-call constraint. Other status transitions need source states that would require activation and are covered by protocol/dry-run tests. A Data API key route, non-fixed caller modes, enabled audio/prediction and draft-only editing have no production mutation proof in this account.

Latest expanded candidate run: 41 PASS, two explicit SKIP (fresh campaign lifecycle and repeated exclusion mutation not opted in). All new catalogs and owned cancelled-fixture reconciliation passed through the real binary, including clear/cancel no-ops. The selected export was empty in this run; earlier nonempty export evidence remains separate. A fresh creation was deliberately not repeated because the one-residue allowance was consumed.
