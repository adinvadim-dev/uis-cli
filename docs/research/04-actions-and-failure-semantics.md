# UIS actions and failure semantics

Researched 2026-10-29. Scope: support communication, call annotations, saved filters/exports, and secondary Medivey blacklist/SIP context. Research only; no product implementation, authenticated account requests, or live mutations. Network work was limited to public first-party documentation and published frontend JavaScript. No account data, credentials, cookies, attachment contents, phone values, or production resource identities are reproduced here.

## Conclusions and evidence strength

UIS support tickets have a concrete private REST contract in the published cabinet frontend. Ticket creation is **two writes**, not one: create the ticket, then create its initial comment with files. The cabinet retains the created ticket only in a component ref, so that protection does not establish durable idempotency. Call annotations have documented public Data API methods; a customer “communication/обращение” in those methods is **not a UIS support ticket**. Saved filters and export jobs also mutate provider state even though fetching report data is a read. [S1–S8, P1–P7]

Evidence labels used below:

- **Documented:** public UIS API/help contract, verified against current pages.
- **Source-observed:** first-party published cabinet code; proves what the client sends/expects, not server guarantees or this account's entitlements.
- **Local-observed:** Medivey's adapter/business logic at commit `54025ac369b572c3dc460a3416743f3e24732026`; this is consumer behavior, not a UIS specification.
- **Proposed policy:** research recommendation for later CLI design. It is not a provider guarantee or authorization to execute an action.
- **Unknown:** not established without additional specs or read-only authenticated validation. In particular, visibility delay, duplicate detection keys, rollback guarantees, notification delivery and exact server validation remain unknown unless stated otherwise.

The existing UIS CLI snapshot at `5d8abd4905e341d735ad5dd208900e41c4ef17a9` contains generated public-method metadata. It omits response schemas, conditional requirements and private cabinet contracts; do not treat it as a complete mutation specification. [L1]

## Common dispatch, confirmation and retry boundary

**Proposed policy for every mutation below:** validate and display the account, target identity and exact intended effect before dispatch; obtain action-specific consent through the eventual CLI confirmation mechanism. Dry-run must remain local. A confirmation is permission to send the reviewed operation once, not permission for unbounded retries, automatic tariff changes, unrelated contact creation, or compensating deletes.

Once dispatch may have occurred, timeout, disconnect, cancellation, malformed success response, an HTTP 5xx, or an internal provider error can leave the result unknown. Do bounded read-after-write reconciliation. If evidence cannot distinguish success, rejection and partial application, return `outcome_unknown`; preserve any known ticket/job/resource ID and stage. Do not claim failure means “nothing changed.” Identical final state can establish a satisfied postcondition without proving which actor caused it. For a repeated request, re-read current state and require a new deliberate decision rather than silently replaying.

UIS uses POST for both JSON-RPC reads and writes. Classify by method semantics, not HTTP verb. JSON-RPC `id` correlates a response; no reviewed contract establishes it as an idempotency key. General errors include validation/permission/auth/component/limit rejection, `duplicate_entity`, `entity_not_found`, and `internal_error`; batch operations are unsupported. A duplicate error is a reconciliation clue, not proof of an earlier identical request. A multi-step action's later rejection says nothing about whether earlier steps committed. [P8]

No reviewed support, annotation, filter or export action supplies an explicit idempotency token. API quotas/required components remain distinct from a direct monetary charge; no account-specific entitlement or price was checked. Source-generated random JSON-RPC IDs, `X-Trace-ID`, and multipart boundaries are not evidence of deduplication. Client code often invalidates/refetches lists after success; this does not establish read-your-writes consistency or a maximum visibility delay. [S3–S8]

## 1. Technical support: concrete private contracts

### Transport and identities

The shell maps support to `/support/ticket`; its `uisAccount` remote exposes `SupportRoot`. The remote resource registry and data-provider config resolve these resources under `https://uis-prod-msk-comagic-api.uiscom.ru/infopin/`. This is **source-observed**, not a supported public API promise. [S1–S4]

The inspected generic provider sends credentialed requests (`withCredentials: true`): create = POST resource, update = PUT resource/ID, list = GET resource with query filters. Support creation/comments use `FormData`: field `request` holds JSON without `files`; each binary is a repeated `files` field. Let the HTTP library choose the multipart Content-Type boundary. Close/reopen use JSON data through the generic update provider. Cookie/session scope, CSRF requirements, authorization on this account, read/unread acknowledgement side-effects of detail/thread GETs, and permission-specific error bodies are **not validated** by these unauthenticated source reads. Do not reuse the old `app.uiscom.ru` bearer token without proving it works for this separate backend. [S3, S4]

Creation form fields are `contact_id`, `phone_id`, `email_id`, `tech_support_web_type_id`, `context`, and optional `files`. All five non-file fields are required by the form; `context` is limited to 500 characters. Available topics come from `GET infopin/tech-support-web-type` filtered by `is_available=true` and `is_trial=true` or `is_active_customer=true`, sorted by `order_num`. Existing contacts/phones/emails are read separately. Topic selection matters: some cabinet topics are requests to activate/deactivate services or change billing, so support communication cannot universally be called financially inert. [S3, S5, S9]

## 4. Secondary context: existing Medivey cabinet mutations

### Blacklist writes are a multi-stage block operation

Private base: `https://app.uiscom.ru/services/ats__callblocking/blacklist/`. Requests use bearer token, X-Requested-With, JSON and cabinet Referer. Read is GET `read/` with `site_id=-1`, phone filter, pagination and sort; adapter normalizes digits and maps an 11-digit leading 8 to 7, then exact-matches `numa`. Its default read limit is 25: this is not a general uniqueness/completeness proof. [M2]

### SIP URI creation supplies a useful ambiguity precedent

Private network resources use `https://app.uiscom.ru/netresources/sipuri/records/`: GET `read/` paginated in 1,000s; POST `create/ {name,phone,short_phone,comment}` and POST `delete/ {id}`. Create has a 20-second timeout. A current success acknowledgement can omit `data`; Medivey then lists and requires exactly one matching name/address to get the actual ID. Before provisioning, business logic lists/adopts a single matching address with the same local-number name prefix, verifies its short number, and conditionally binds locally. No server idempotency key. This is local recovery logic, not an atomic dedupe guarantee. [M6, M7]

Creation affects routing configuration and may have tariff/license implications, but the source does not establish a price. Deletion can break routing and must be separately authorized. Readback of a registered URI is **not** proof a call connects. On bind failure, compensation deletes only a newly created resource confirmed unbound; an uncertain bind/read preserves it. Reused resources are never compensation targets. After an ambiguous create, first recover identity by a complete list; multiple candidates are a conflict, not grounds to create another. [M6, M7]

Legacy employee provisioning is a different multi-write path: `create.employees` → `update.employees` (replaces full phone list) → local conditional bind, with best-effort orphan deletion. If create response is lost, the helper lacks the new ID for cleanup. The generic `createEmployee` branch that accepts a phone number retries **any error** by sending a second create DTO without phone numbers; that can duplicate an employee after an uncertain first write. Do not copy this fallback as retry policy. The current SIP URI route must not be conflated with this legacy employee identity or public `create.sip_lines`. SIP password rotation also cannot safely be repeated after an ambiguous response: it may invalidate working credentials again. [M3, M7, M8]

### Session refresh can replay a compound write

`withUisPrivateSession` reruns its whole callback once after a cached session returns status 401 **or 403**. It does not distinguish an auth rejection on the first dispatch from an auth error on a later read/write in a compound callback. Thus private blacklist create may have committed before a read/update fails and the whole add callback is re-entered. SIP URI create itself is not retried after a plain timeout, but the wrapper still replays a direct 401/403 failure. This is existing consumer behavior, **not evidence of safe provider idempotency**. A CLI adapter should authenticate/preflight separately and never use callback-level automatic replay around a dispatched compound mutation. A 403 may indicate permission denial rather than an expired session. [M1, M2, M6]

## Remaining unknowns / handoff constraints

The source now supports designing typed ticket create/reply/close/reopen and attachment contracts, but authenticated **read-only** validation still needs to prove the selected principal, backend cookies/CSRF, entitlement, response schemas and ID namespaces. No live writes are necessary to validate static request shapes. If later testing requires sending support messages or changing account configuration, obtain authorization for that exact reviewed action first.

Before enabling mutations, resolve or fail closed on: real ticket/comment IDs versus generic UI fallback; support list completeness and namespace collisions; attachment server limits and partial acceptance; write visibility bounds; comment replacement semantics; tag-deletion cascade and sale uniqueness; saved-filter ownership; export task recovery when initial ID is lost; schedule delivery/disable semantics; and whether private-facing RPC methods are accepted with the intended auth. No automatic purchase, limit expansion, tariff change, transcription, support rating, contact creation, or external export follows from an ordinary read/search action.
