# Employees: action safety and data boundary

Research date: 2026-11-05. Scope: operational employee, employee-group, employee SIP-line and softphone commands. This track inspected local source only. It did not retrieve credentials, open private response files, issue authenticated requests or perform provider mutations. Private cabinet endpoint discovery belongs to the authenticated-surface track; unobserved endpoint names below remain unknown.

## Evidence and scope

The inspected CLI base is `2802611c74390602edd62417a246b66f8e08112b`; the Medivey consumer reference is `b9c0928cdadd4dcedd3618ba588b37966d40de24`. Existing CLI code is primary evidence of its own safety behavior, not a UIS guarantee. Medivey consumer code establishes historical request usage, not current private-cabinet compatibility. A bounded filename scan found no relevant cached public UIS JavaScript under `/tmp`; no private JSON capture was opened. Public documentation and current authenticated/frontend evidence must supply the exact employee and softphone DTOs.

The requested scope is current-state diagnosis and deliberate configuration changes. It does not authorize a live production mutation merely for test coverage. Preserve a clear distinction between employee availability, SIP registration and actual call reachability: none is proof of the other. Do not label missing registration data as `unregistered`.

## Dispatch and ambiguity policy

Reuse the existing private command pattern: parse and validate locally; construct a plan containing action, target IDs and payload **field names only**; return dry-run before profile/session/credential/network I/O; require confirmation or explicit `--force` for a real write; then obtain the bound private client. `--force` is confirmation, not a bypass for account binding, capability validation or preflight. Ordinary reads must not start login implicitly. [C1, C2]

The current CLI binds the saved session login to the account profile and supplies a live authenticated support-metadata probe before writes. That is credential-binding plus a successful authenticated read, not independently provider-reported principal identity or proof of permission for employee edits. Retain that boundary and add surface-specific read/schema/target checks; do not weaken it because another endpoint accepts the token. App, Go and cabinet JWT token sources are distinct. No employee CSRF exemption is established by existing support preflight. [C1, C3]

Send a mutation once. HTTP timeout, cancellation after dispatch, disconnect, 5xx, malformed response or an acknowledgement without the requested effect requires bounded fresh read-back, not another send. A JSON-RPC request ID is correlation, not a proven idempotency key. Read-back may establish that the desired state now holds; it cannot prove which actor caused it. Return `verified: true` only when requested persisted fields match for the exact target. Otherwise return exit 9 (`outcome_unknown`) with safe target identity and stage, preserving enough information for deliberate reconciliation. Provider auth/permission/validation rejection stays distinct from transport ambiguity. [C3, C4]

If the request context is cancelled or exhausted, reconciliation needs its own bounded cleanup context; reusing a cancelled context cannot prove the effect. Treat multi-write edits as non-atomic: if one stage may have committed, a later rejection must retain partial/unknown status. Do not replay an entire callback around session refresh. The Medivey `createEmployee` legacy fallback resends create after any first error; this is a warning example, not a pattern to copy. Its `setEmployeePhone` overwrites the complete phone list and must not be used for partial edits without preserving the current collection. [M1, M2]

No observed contract here promises idempotency, optimistic concurrency, immediate visibility, rollback or a maximum registration lag. Keep these limitations explicit. Test response loss, effect mismatch, wrong target ID, schema drift, forbidden/auth failure and cancellation with a scripted HTTP server; live read success is not live-write proof.

## Secret boundary

Use a typed, allowlisted output projection for employee cards, softphone settings and line diagnostics. The current `archive.Scrub` strips password/token/cookie/CSRF and URL-shaped keys, but retains arbitrary values under `phone`, `phone_number`, `login` and other ordinary fields. SIP URI or credential data can therefore survive generic scrubbing. The dry-run `redactParams` likewise removes credential-shaped keys but does not guarantee removal of SIP URI values. Do not emit or archive raw employee/line DTOs through these helpers. [C2, C5]

Exclude SIP URIs/addresses, authentication usernames/logins, passwords, provisioning/download URLs, cookies, tokens, CSRF, device configuration bodies and raw provider errors. Names/contact fields can contain arbitrary text, including embedded URIs; an allowlisted field name alone does not guarantee a safe value. Redact or reject sensitive value patterns before rendering. Error paths, rejected payloads, confirmation plans, JSON/human/plain output, test fixtures, traces, screenshots and research documents share this boundary. Keep any required complete provider DTO only in memory inside the adapter. Tests should use synthetic markers and verify no secret survives success, error, dry-run, nested arrays or read-back output.

## Direct versus archive decision

Recommend explicit **live** commands for employee card, membership, softphone settings and registration snapshots, with no new archive or background sync in this task. The acceptance scenarios need current provider truth and deliberate actions; replaying old `registered` state from a local database would obscure the incident. Help and output must make the network boundary clear and include observation time/source. Current configuration lists are operational catalogs, not a requested independent historical collection.

Named deferrals: employee/group revision history, SIP registration/event history, audit trails, endpoint provisioning files and bulk/offline employee exports. No historical collection, cursor, retention guarantee, tombstone feed, asset list or late-arrival mechanism for these surfaces has been established in this track. If authenticated research finds useful durable history, add it to the final synthesis as an explicit deferral rather than silently discarding it. An archive would then need its own privacy/retention decision, stable `(account, entity ID)` identity, collection-specific completeness, transactional checkpoint and freshness semantics. No current registration-state read may claim historical completeness.

The existing support archive is a separate collection and remains untouched. Prior research inspected crawlkit v0.16.5, whose toolchain requirements did not fit this CLI, and this checkout has no local crawlkit source. This track did not verify the current upstream tag and recommends no crawlkit dependency/toolchain change for a direct-only extension. Do not present the earlier tag as the current latest release.
